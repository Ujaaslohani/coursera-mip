The Whole System, One Story

Follow one click, all the way through

This is what happens when someone types a question into the Query Workspace and hits "Ask." Every other endpoint in this app follows the same shape — this is just the most complete example, so it's the clearest way to see the whole system at once.

🖥️
You click "Ask"
In the browser, on the Query Workspace page
↓
📡
The API client sends the request
frontend/lib/api.ts — attaches your login token, calls the backend over HTTP
↓
🚪
The backend checks who you are
POST /api/query — confirms your login, then checks your role is allowed to search
↓
🧭
An AI agent plans the search OpenAI · gpt-4o-mini
A real API call, using your OpenAI key — decides how many results to fetch and the best phrase to search for, before anything is searched
↓
🔍
The database is searched two ways at once
OpenAI · text-embedding-3-small matches by the meaning of words (transcripts, OCR'd slide text, quiz text, discussion posts)
Local model · CLIP ViT-B/32 — no API key used matches by what an image actually looks like, pixels only
Results from both are then combined into one list.
↓
📊
Results are reordered for fairness Plain code — no AI call
So one modality (like video) can't crowd out a relevant forum post or quiz question
↓
✍️
An AI writes the answer OpenAI · gpt-4o-mini
A second real API call — using only that retrieved evidence, never the whole database, and citing exactly where each claim came from
↓
🛡️
A second check runs Plain code — no AI call
Not an AI — a rule that removes any citation that doesn't actually match retrieved evidence, before a human ever sees it
↓
🗄️
Everything is saved
The question, the evidence links, the answer, and a permanent record of the action — all in Postgres
↓
📱
You see the answer
Back in the browser — the plan, the cited evidence, and the confidence score, all visible
Any other action
register an asset, review a recommendation, check metrics…
→↓
Same 3 first steps
Browser → API client → backend route (auth + role check)
→↓
A simpler middle
One service function, no AI agents needed
→↓
Same last 2 steps
Saved to Postgres → shown back in the browser

The Query Workspace is the longest path through the system — everything else is a shorter version of this same shape.

The Other Half Of The System

Before anything is searchable — the Intake flow

A question can only be answered from evidence that's already been through this flow. This is what happens between someone uploading a video and that video's content showing up in a search result.

📤
You register an asset
Asset Intake page → POST /api/assets — modality, owner, and where the file lives
↓
🔁
The backend checks for a duplicate Plain code — no AI call
Same owner + modality + file already registered? Reuse it instead of creating a copy
↓
🗄️
Saved, stage "uploaded"
A new Asset row and a ProcessingJob row are written — nothing processed yet
↓
⚙️
You start processing
POST /api/processing-jobs — this is where the real work happens, all in one call
↓
🔀
The right tool runs, based on modality
🎬 Video → ffmpeg (local) pulls frames, then OpenAI · Whisper transcribes the speech
🖼️ Image → tesseract OCR local reads any text, CLIP looks at the picture itself
📑 Slide (PDF) → PyMuPDF local pulls the text out directly
✅💬 Quiz / Discussion → cleaned and de-duplicated local code
↓
🧮
Everything gets turned into numbers
OpenAI · text-embedding-3-small embeds the text; images additionally get a local CLIP embedding of the actual picture
↓
🗄️
Saved as Segment rows
Each one stamped with the job that created it — this link is what lets the system track lifecycle stages correctly later
↓
✅
Job reaches "searchable"
From this moment on, this asset's content is part of every future cross-modal query
No system binary?
ffmpeg / tesseract missing on PATH
→↓
Job fails visibly
Stage → "failed", with a plain-English error saved — never silently skipped

This is a deliberate design choice: an asset that can't actually be processed should never look "done" in the dashboard.

2
POST /api/processing-jobs

Run the pipeline — this is where the real work happens

The single biggest function in the codebase. Resolves the file, routes to the right modality-specific pipeline, normalizes the output, embeds it (text + CLIP for images), and advances the job through five stages in one synchronous call.

POST/api/processing-jobs
start_processing_job() backend/app/api/processing_jobs.py
→ run_processing_job() backend/app/services/processing_service.py
→ get_storage_backend().resolve() storage_service.py — finds the real file
→ modality routing:
ModalityPipeline function calledNeeds
videopipelines/video_processing/extract.py :: process_video()ffmpeg + Whisper API
imagepipelines/image_processing/extract.py :: process_image()tesseract OCR + ai/embeddings/clip_embed.py
slide (PDF)pipelines/image_processing/extract.py :: extract_slide_text()PyMuPDF only
quizpipelines/text_processing/clean.py :: process_quiz()none
discussionpipelines/text_processing/clean.py :: process_discussion_thread()none
transcriptalready normalized JSON — passed straight throughnone
→ normalize_raw_units() ai/preprocessing/normalize.py — one consistent shape for every modality
→ embed_segment() ai/embeddings/embed.py — OpenAI text-embedding-3-small, 1536-dim
→ (images only) embed_image() ai/embeddings/clip_embed.py — local CLIP ViT-B/32, 512-dim
→ writes one Segment row per unit, stamped with job_id
→ advance_job() ×4 app/jobs/job_queue.py — preprocessed → embedded → indexed → searchable
Real response (this session){ "job_id": "fcf12151-b0e0-4c52-b089-269676193e0e", "asset_id": "8ff9f4ec-c447-4342-85df-830be010caf6", "stage": "searchable", "error": null }
Writes to: segments (embedding + image_embedding columns) processing_jobs (stage updates) audit_log

Fails visibly: if ffmpeg/tesseract aren't on PATH, or the file doesn't resolve, the job goes straight to stage failed with a human-readable error string — never silently skipped.

3
POST /api/query

Ask a question — the agent pipeline kicks in

Not a single search call. A planner agent decides strategy first, retrieval runs two independent searches (text-meaning + CLIP visual), then a ranker agent re-orders for cross-modal diversity.

POST/api/query
frontend/app/query/page.tsx → runQuery() lib/api.ts
→ submit_query() backend/app/api/query.py
→ run_query() backend/app/services/retrieval_service.py
→ plan() ai/agents/retrieval_planner.py — real GPT-4o-mini call, decides top_k + search terms
→ retrieve() ai/retrieval/retriever.py — runs _text_channel() + _visual_channel() in parallel, merges by segment_id
→ rank() ai/agents/evidence_ranker.py — diversity-aware re-order, then sliced to top_k
→ mark_segments_retrieved() lifecycle_service.py — advances each cited job's stage
Request body{ "question_text": "Why are learners struggling with backpropagation?", "top_k": 5 }
Real response (truncated){ "query_id": "f1b9197e-...", "retrieved_evidence": [{ "segment_id": "7bb20790-...", "modality": "transcript", "text_content": "Today we're covering backpropagation...", "similarity": 0.635, "match_type": "text" }], "agent_plan": { "search_terms": "learners struggling backpropagation concept", "top_k": 10, "reasoning": "The question is moderately specific..." } }
Writes to: queries (the question itself) processing_jobs (stage → retrieved) audit_log

RBAC: requires query:run — educator, reviewer, or admin.

4
POST /api/synthesize

Turn evidence into a grounded answer

The LLM only ever sees the evidence array from the previous call — never the full database. A validator agent then checks its own output before anything is saved.

POST/api/synthesize
synthesize_endpoint() backend/app/api/synthesize.py
→ synthesize_insight() backend/app/services/synthesis_service.py
→ synthesize() ai/synthesis/synthesizer.py — GPT-4o-mini, response_format: json_object, prompt built by ai/prompts/synthesis_prompt.py
→ validate() ai/agents/quality_validator.py — calls score_groundedness() from ai/evaluation/evaluate.py; strips any citation not in the retrieved set, caps confidence at 0.3 if it had to
→ mark_segments_synthesized() lifecycle_service.py
→ writes one Insight row, status="pending_review"

POST /api/review-feedback

A human closes the loop

The only endpoint that changes an insight's status from pending to something operational — and the only one gated to the reviewer role specifically.

POST/api/review-feedback

→ submit_feedback() backend/app/services/review_service.py — writes ReviewFeedback, flips Insight.status
→ mark_segments_reviewed() lifecycle_service.py — every asset cited by this insight reaches its final tracked stage

6
GET /api/metrics · GET /api/audit-log

Reading it all back out

Two read-only endpoints power every dashboard. Neither has its own table — both aggregate live from the tables every other endpoint already wrote to.

GET/api/metrics
get_metrics() backend/app/api/metrics.py → compute_metrics() backend/app/services/metrics_service.py — COUNT() queries across processing_jobs, review_feedback, assets, segments, insights

Reference

Terms an onboarding engineer will hit fast

match_type
On each evidence item — "text" (OpenAI text-embedding match) or "visual" (CLIP image match). See ai/retrieval/retriever.py.
JobStage progression
An ordered list in models.py (JOB_STAGE_PROGRESSION) — lifecycle_service only ever moves a job forward along it, never backward.
CurrentUser
Decoded JWT payload — auth/dependencies.py. Carries user_id, roles[], permitted_sources[].
permitted_sources
Course/asset-level access list on the JWT — checked inside retriever.py before evidence ever reaches synthesis. Separate concept from RBAC roles.
StorageBackend
Interface in storage_service.py. LocalFilesystemStorage is what's live; S3CompatibleStorage exists but needs OBJECT_STORAGE_URL/KEY, unset in this env.
requires_db fixture
tests/conftest.py — skips a test if TEST_DATABASE_URL isn't set, since Segment's Vector columns have no sqlite equivalent.
